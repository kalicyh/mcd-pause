# 聊天提醒与浏览器点餐

## 聊天内的简单操作

定时饭点提示使用宿主 visualize；读其指南后生成并在聊天中呈现：

```sh
python3 "$SKILL_DIR/scripts/mcpause.py" render-reminder --meal lunch --out /ABSOLUTE/TASK/VIEW/mcpause-reminder.html
```

按钮为“开始点餐”“20 分钟后提醒”“这餐已安排”。按钮回传简短请求；延后和已安排按 [定时任务](automations.md) 执行，不以按钮变色代替真实调度。提醒本身不启动浏览器。

用户点击开始、说“我要吃饭”或主动提出想吃的餐品后，直接打开浏览器，不再多问一次是否选餐。只问缺少的位置、方式等关键数据。只问价格或解释梗时不擅自打开。界面不可用时用文字继续。

## 真实完整菜单

按 [用餐流程](meals.md) 取得当前门店的 query-meals 与餐品详情。catalog 保留所有返回餐品和 categories 的真实顺序/成员，不只保留某个关键词，不用营养分类替代官方分类。未知价格显示待核价，带 canWithOrder 的餐品保留展示，但不自动加卡。

--keyword 四件套表示在完整菜单前增加“你想吃的 · 四件套”，不是过滤全菜单。Agent 从用户本次语义提取实际品类；未命中时仍显示完整菜单，不替换用户需求。推荐中只把有证据的新品前置：新品/上新/全新登场标签，或 campaign-calendar 的当前明确新品证据；热卖和编号大小不是新品证据。预算、忌口和营养约束用于推荐，完整菜单仍可浏览；未知营养不能宣称满足目标。

餐品图片使用 MCP 返回的确切 https://menu-img.mcd.cn/pcm/ URL，直接在浏览器加载。套餐主图注明默认搭配；无对应子项图片就显示文字，不猜 URL、不用其他规格替代。聊天内资源限制无法加载这些图片，不下载或代理绕过。

预取当前选择及少量首屏详情，按编码存入 details.json。其他商品在点击后经本机会话读取。菜单与详情为独立页面，返回保留搭配。单选套餐、多选多份轮次、配料和冰量按详情参数编辑；复杂轮次预估价未知时用官方核价。换饮料仅保留兼容冰量。购物餐单保存不同搭配及数量，改配后旧报价失效。浏览器自动核价，不显示常驻的重新核价/刷新价格按钮；失败时提供重试。价格和费用组成一组，“加入餐单”与整组内容垂直居中。

## 临时浏览器会话

```sh
python3 "$SKILL_DIR/scripts/mcpause.py" prepare-browser --catalog work/catalog.json --details work/details.json --keyword 四件套 --selected REAL_PRODUCT_CODE --out work/browser-session.json
python3 "$SKILL_DIR/scripts/serve_view.py" --session work/browser-session.json --state-dir work/browser-state
```

prepare-browser 可带 --new-products、--quote、--card-comparison。用户要求送达庆祝后才带 --celebrate-delivery。核价证据见 [开卡优惠](membership.md)。会话文件以 0600 保存，不提交仓库或公开分享。

优先复用已有 MCP 连接。本机进程使用 MCD_MCP_TOKEN 或 --token-stdin 的不回显输入；宿主提供已有凭据时只在进程内传给 Client，不写入会话 JSON、页面、URL 或日志。连接不可用时报告具体阻断，不安装依赖或修改全局配置。

用 open_in_codex 的 browser 目标打开返回的 127.0.0.1 URL。此进程只监听随机本机端口，提供当前页面及限定操作，不开放目录、不注册 MCP/系统服务、无需远程部署。页面经同源会话校验调用脚本，脚本请求官方 MCP；查详情、核价、开卡对比和进度直接更新浏览器，不向聊天发送整段 JSON。

只查询时使用只读会话；“保存餐单”写 browser-state/selection.json，用户回聊天继续时直接读取。正常点餐且用户希望在浏览器完成下单时，核实配送/取餐参数后启用下方订单确认入口，不要一直沿用早期只读测试配置。

需要浏览器完成订单确认时，先核实同门店的配送或取餐参数，将 addressId 或 takeWayCode、可选备注写入私有 checkout JSON；准备会话时带 --checkout，启动时带 --allow-orders。开卡优惠随搭配和整单自动计算，明细默认折叠。默认不开卡，用户可勾选已核实卡项，含卡总额随选择更新。点击“去结算”只生成五分钟确认单：突出配送地点、餐品图、套餐组成、已选卡费与实付，配料/冰量及费用明细可展开。点击最终“确认下单”才提交一次。用户只查询或明确不下单时，不启用该开关；选择不开卡仍能按普通餐单下单。

订单创建后显示官方支付链接，保留在餐单下方，关闭确认框或刷新页面后仍可返回。支付由用户本人操作；未返回有效官方链接时指引到官方 App 核对，不拼造链接。结果不确定后停止，不能重试提交；价格或卡种/卡费变化后重新比较、重新确认。进程两小时无请求自动退出；用户结束测试时停止对应进程。页面断开时由 Skill 重新打开，不称有常驻后台服务。

## 订单进度与送达庆祝

订单页可输入真实订单号或主动查询最近订单。展示官方状态、取餐码、预计时间，不伪造进度百分比、倒计时、骑手坐标或路线。2026-10-14 的 query-order schema 有状态和预计时间，没有配送轨迹/地图接口；当前显示状态时间线并说明地图不可用。

“持续跟进”在页面打开时每三分钟检查，隐藏页面暂停网络检查；终态、两小时、30 次成功查询或查询失败后停止。关闭页面不承诺继续运行。后台跟进另按 [定时任务](automations.md) 创建用户授权的宿主调度，避免重复跟进。

送达礼花需要先观察到当前订单未完成，再读到明确“已送达”，或官方 orderStatus=6 且证据表明是外送。先原子占用庆祝事件，再播放一次。首次查看已完成历史订单、到店自取完成、取消、刷新与重复查询不触发。减少动态效果时只显示送达文字。

## 其他模式

render-shop 仍可输出聊天内文字选餐或 --standalone 静态图文预览；静态预览无 API，仅提供复制请求的后备路径，不称已自动核价。日常使用优先上面的浏览器会话。

营养小游戏可用 render --catalog ... --out ... 按需展示。demo --inline 使用明确虚构数据，不联网、下单或创建提醒，不能当作真实菜单/订单。
