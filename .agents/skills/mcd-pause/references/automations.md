# 饭点提醒与订单跟进

这是宿主能力，Skill 和 HTML 本身没有后台调度器。使用当前 Codex 聊天的 heartbeat 定时任务；没有该能力时说明当前只能手动触发，不把一段提醒文字说成已创建提醒。

## 开启饭点模式

用户明确要求自动提醒后，确定餐次、饭点、提前多久、工作日与时区，复用已给出的设置。默认偏好里的提醒为关闭；示例时刻不代表用户选择。不要根据没有麦当劳订单推断用户未吃饭。

1. 使用 `profile --file <json>` 保存设置，时区采用用户或客户端提供的值。例如当前用户 Asia/Singapore；不能读取运行主机的本地时间代替。
2. 按宿主要求先查找 `automation_update`，检查已有相同用途的任务，优先更新。每个餐次采用每天一次的同聊天任务，触发时间是饭点减提前量，避免全天高频唤醒模型。
3. 记录工具返回的自动化 ID 到当前任务的私有状态/记忆中，后续调整、暂停和删除使用真实 ID。工具未确认成功前不能称提醒已启用。桌面本地任务需要电脑与应用保持运行。

给调度器的提示词应是自然语言，包含技能绝对路径或明确技能名、餐次、时区和停止条件。例如：

> 使用 $mcd-pause 检查本餐。先执行 reminder tick --meal lunch。action=none 时保持静默，不连接 MCP。action=recommend 时只查询当前门店菜单、可用优惠和营养，准备少量符合已保存偏好的候选；缺少关键位置或取餐方式时只询问必要信息。用聊天内简洁提醒卡提示开始点餐、延后或标记已安排；确认吃饭后再打开浏览器图文菜单。不得自动创建订单、领券、兑换积分或支付。连接失败时如实简短报告本次问题，不循环重试，不重复创建提醒。

具体调度参数交给宿主工具，不向用户输出原始调度指令。初始化偏好不是创建任务；明确区分两者。

## 延后与停止

`reminder snooze --meal lunch --minutes 20` 返回 `schedule_once` 和带时区的时间。除了保存状态，还需使用宿主在同聊天安排**一次**到时检查；如果已有同餐延后任务则更新。不要改变用户的每日饭点设置。

`reminder done --meal lunch` 标记这餐已安排。用户说已吃、带饭或不想再提醒时执行它，并撤销同餐还未触发的临时延后任务。每日饭点任务保留，除非用户要整体关闭。取消全部提醒时更新 profile，并暂停/删除对应真实自动化。

脚本按本地餐次日期去重。免打扰时段、非提醒日、本餐已处理和错过窗口返回 none。用户临时要求马上查询时直接完成查询，无需修改长期开关。

## 持续跟进订单

用户请求持续跟进，或明确启用此功能后，为本单创建同聊天的有限期 heartbeat。建议三分钟一次，每次先运行 `order watch`；原生 MCP 路径先运行 `order poll-check --order-id ...`，只有 poll=true 才查询并执行 `order observe`，查询或解析失败则执行 `order poll-failed` 记录连续失败。

提示词必须包含：真实 orderId、本技能位置、只读查询、状态不变保持静默、状态变化才更新界面，以及终态/两小时/30 次成功检查/连续三次失败的停止条件。`order watch` 返回 stop=true 时通过宿主删除或暂停本单临时自动化，告知真实原因。未知状态不得视为终态。

礼炮只在跟进中的外送订单确认送达时播放，由事件去重保证同一单一次；支付、接单和历史已完成订单不触发。终态检查前处理本次送达事件，再停止调度。用户关闭庆祝、应用没有该工具或减少动态效果生效时，使用文字状态。聊天提醒的更新需要宿主执行；浏览器临时会话可以在页面打开时经本机脚本查询并更新。浏览器和宿主共享同一任务状态目录，避免重复查询或重复庆祝。页面关闭后不保证浏览器跟进继续。
